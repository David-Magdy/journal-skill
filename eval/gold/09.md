# S3 Presigned URL Signature Mismatches with Temporary STS Credentials

## Conceptual Core
Temporary AWS credentials generated via STS (`ASIA...`) require both the access key, secret key, and the security token (`X-Amz-Security-Token`). When signing S3 presigned URLs with temporary credentials, SigV4 places authentication tokens and signatures into query parameters. If an HTTP client simultaneously provides a redundant or conflicting `Authorization` header during request dispatch, S3 attempts to validate the header signature rather than the query parameters, triggering an immediate `SignatureDoesNotMatch` failure.

## Bug / Edge Case Encountered
An automated HTTP upload client injected a default authorization header alongside an S3 presigned URL generated with temporary credentials (`AWS_ACCESS_KEY_ID=[REDACTED_ACCESS_KEY]`, `AWS_SECRET_ACCESS_KEY=[REDACTED_SECRET_KEY]`, `AWS_SESSION_TOKEN=[REDACTED_SESSION_TOKEN]`). Stripping the extraneous header allowed AWS SigV4 query-parameter authentication to succeed.

## Key CLI Commands & Environment Tricks
- Generate presigned URLs using temporary STS credentials:
  ```bash
  aws s3 presign s3://[REDACTED_BUCKET]/upload.bin --expires-in 3600
  ```
- Upload to presigned URLs with explicit header stripping:
  ```bash
  curl -v -X PUT -H "Authorization:" --upload-file upload.bin "<presigned_url>"
  ```
