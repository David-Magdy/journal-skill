# SQLite WAL File Explosion and Checkpoint Starvation from Dangling Reads

## Conceptual Core
In SQLite Write-Ahead Logging (WAL) mode, write operations append to `-wal` files and are asynchronously merged into the main database during checkpoints. SQLite cannot checkpoint frames past the frame pointer of the oldest active read transaction without corrupting the read view of concurrent readers. When an application leaves a read transaction unclosed (e.g. streaming cursors wrapped around slow network operations), checkpoints stall and the WAL file expands indefinitely.

## Bug / Edge Case Encountered
A worker thread lazily iterated over an open SQLite cursor while executing blocking HTTP requests within the loop body. Holding the read transaction open prevented automatic checkpointing, causing `app.db-wal` to grow to 18 GB and exhaust disk volume capacity.

## Key CLI Commands & Environment Tricks
- Check uncheckpointed WAL frames and blocking reader status:
  ```sql
  PRAGMA wal_checkpoint(PASSIVE);
  ```
- Flush pending transactions and truncate WAL storage to zero:
  ```sql
  PRAGMA wal_checkpoint(TRUNCATE);
  ```
- Guard against reader-writer deadlocks:
  ```sql
  PRAGMA busy_timeout = 5000;
  ```
