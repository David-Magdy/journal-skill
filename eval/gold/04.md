# Goroutine Leaks from Unbuffered Channel Writes on Context Cancellation

## Conceptual Core
In Go concurrency patterns involving fan-out workers, writing to an unbuffered channel requires an active receiver. If a parent function exits early due to context cancellation, timeout, or processing only the first arriving response, any unbuffered channel write inside surviving worker goroutines blocks indefinitely. Blocked goroutines are never garbage-collected; their initial 2KB+ stacks and referenced heap closures accumulate into an out-of-memory crash.

## Bug / Edge Case Encountered
When spawning $N$ worker goroutines to query data shards concurrently, the coordinator exited as soon as the first result arrived or upon `ctx.Done()`. Using an unbuffered channel `ch := make(chan Result)` caused all remaining $N-1$ worker goroutines to block forever on `ch <- res`, accumulating 140,000+ zombie goroutines under production traffic.

## Key CLI Commands & Environment Tricks
- Inspect active goroutine counts and stack traces in running Go binaries:
  ```bash
  curl -s http://localhost:6060/debug/pprof/goroutine?debug=1 | head -n 30
  ```
- Interactive web inspection of goroutine blocking points:
  ```bash
  go tool pprof -http=:8081 http://localhost:6060/debug/pprof/goroutine
  ```
